- 문서 상태: 현재 신청서 방향을 정리한 기획본. 개발 예정 기능을 구현 완료로 표시하지 않는다.

> 지원장바구니는 정책 지원이 필요하지만 시작하기 어려운 청년이 적은 카드 선택으로 상황과 목표를 정리하고, 필요한 공공지원과 준비·상담 등 다음 행동을 시작하도록 돕는 AI 에이전트이다.

| AI 역할 | 확인된 상황·목표와 부족한 정보를 정리하고, 필요한 지원 방향·상세 확인 질문·다음 행동을 제안 |

## 3. 대상자와 실제 서비스 이용자 구분

### 3.1 지원 대상

지원의 수혜 대상은 청년이다. 초기에는 서울 거주 만 19~34세 중 정책을 적극적으로 탐색하지 않거나 이용 경험이 적은 사람을 대상으로 한다. 정책을 찾아봤지만 조건 확인·서류 준비에서 중단한 사람도 검증에 포함한다.

미취업자만으로 제한하지 않는다. 학교에 다니거나 일하고 있는 청년도 해당 정책의 조건과 상황에 따라 포함한다. 정책 이용 경험이나 탐색 부담을 참가자 모집 시 확인할 구체적인 문항은 별도로 정한다.

### 3.2 청년 직접 이용과 상담 담당자용 활용

사용자가 추가한 ‘청년에게 배포 또는 상담기관 담당자에게 배포’는 두 가지 운영 방향이다. 현재 신청서의 이용 흐름은 **청년 직접 이용**을 기준으로 작성되어 있다. 상담 담당자용 서비스까지 확정된 것으로 해석하지 않는다.

| 구분 | 청년 직접 이용 | 상담 담당자용 활용 |
|---|---|---|
| 서비스 조작자 | 청년 본인 | 청년센터·대학 상담창구 등의 상담 담당자 |
| 입력 | 본인이 상황·관심·목표 카드를 선택 | 청년과 확인한 상황을 담당자가 입력하거나 함께 선택 |
| 핵심 결과 | 필요한 지원, 추가 질문, 준비물·발급 안내, 상담·문의 준비 | 확인된 상황 요약, 정책 후보, 남은 질문과 준비물 |
| 검증 초점 | 질문 부담·이탈·정책 도달·실제 준비와 상담 시작 | 상담 준비와 상황 파악에 도움이 되는지, 청년의 부담이 줄어드는지 |
| 현재 상태 | 신청서와 개발 흐름의 작성 기준 | 검토할 운영안. 담당자 전용 화면·권한·저장 방식은 미정 |

**미정:** 1차 웹 MVP를 청년 직접 이용으로 할지, 상담 담당자용으로 할지 결정한다. 양쪽을 동시에 구현한다는 약속은 하지 않는다. 상담기관은 청년 직접 이용형에서도 유입·실증 협력 창구가 될 수 있다. 현재 협약이나 도입이 성사된 기관은 이 문서에서 주장하지 않는다.

## 4. 핵심 사용자 흐름과 화면

### 4.1 기본 시작안: 상황 카드

첫 질문: **요즘 어떻게 지내고 있나요?**

- 학교에 다녀요
- 일하고 있어요
- 쉬고 있어요
- 답하기 어려워요

다음 관심 카드:

- 생활비 부담 줄이기
- 부담 적은 활동 찾기
- 사람에게 상담받기
- 잘 모르겠어요

### 4.2 비교할 시작안: 목표 카드

첫 질문: **지금 가장 이루고 싶은 것은 무엇인가요?**

- 취업하기
- 나만의 공간에서 생활하기
- 새로운 기술 배우기
- 잘 모르겠어요

두 질문을 모두 반드시 먼저 묻는다는 의미는 아니다. 상황 중심 시작과 목표 중심 시작 중 부담과 이탈을 줄이는 방식을 사용자 테스트로 확인한다. 카드의 문구·개수·순서는 테스트를 통해 조정한다.

### 4.3 이후 흐름

~~~mermaid
flowchart TD
    A["상황·관심 또는 목표 카드"] --> B["지원 방향·기초 조건 확인"]
    B --> C["관심 정책·지원 방향 선택"]
    C --> D{"더 자세히 확인할까요?"}
    D -->|"사용자가 선택"| E["기존 답변을 이어받아 상세 질문"]
    D -->|"현재 안내로 계속"| F["확인된 정보로 정책·행동 안내"]
    E --> G["조건·선호 반영 후 정책·행동 재정리"]
    G --> H["준비물·발급 경로·상담 준비"]
    F --> H
~~~

- 상세 설명이나 정책명 입력을 이용 시작의 필수 조건으로 두지 않는다.
- 나이·거주지 등은 필요한 단계에서 확인한다. 초기 대상이 서울 청년이라고 해서 사용자의 실제 거주 조건을 자동으로 가정하지 않는다.
- 이미 확인한 내용을 반복해서 묻지 않고, 한 번에 질문 하나를 제시한다.
- 충분한 정보가 있으면 정책과 다음 행동을 보여준다. 질문을 계속 늘리는 것을 목표로 하지 않는다.
- ‘최소 질문’은 모든 사용자에게 동일한 질문 수를 보장한다는 뜻이 아니다. 진입 단계의 부담을 줄이고, 필요한 정보가 생기면 질문을 단계적으로 확장한다. 실제 질문 수·부담·이탈과 추천 품질을 함께 측정한다.
- 정보가 부족하면 부족한 이유와 확인 방법을 보여준다. 이용 자격이 확인되지 않은 정책을 확정적인 지원 대상으로 안내하지 않는다.

### 4.4 핵심 보완: 최소 질문에서 선택적 상세 질문으로

**최소 질문 카드는 서비스 진입을 쉽게 만드는 시작 화면이다. 관심이 생긴 사용자가 계속 간단한 카드에만 머무르도록 제한하지 않는다.**

입력 정보가 적으면 사용자의 조건·목표·선호를 충분히 구분하기 어려워 정책 우선순위와 다음 행동 제안의 품질이 제한될 수 있다. 이를 실제 성능 저하가 이미 확인된 결과로 단정하지 않고, 상세 정보 보완으로 개선할 수 있는지 검증할 가설로 둔다. 질문을 늘리는 것 자체가 정확성 향상을 보장하지는 않는다.

| 단계 | 목적 | 질문·화면 | 결과 수준 |
|---|---|---|---|
| 1. 간편 시작 | 관심을 갖고 첫 선택을 할 수 있게 함 | 일상적인 상황·관심·목표 카드, 모름·건너뛰기 | 지원 방향과 기초 안내. 부족한 조건을 표시 |
| 2. 전환 제안 | 사용자가 더 알아볼 의향이 있는지 확인 | 관심 정책 선택·혜택 확인·준비 안내 요청 등 명시적 행동 뒤 상세 확인을 제안 | 필요한 정보와 질문 목적을 안내 |
| 3. 상세 확인 | 후보와 실행 경로를 구분할 조건·선호를 보완 | 기존 답변이 채워진 단계형 화면. 조건별 선택지·짧은 수치 입력·선택적 자유 입력 | 확인된 조건과 남은 질문, 사용자 선호 정리 |
| 4. 결과 갱신 | 추가 정보로 정책·다음 행동을 다시 정리 | 변경된 추천 이유·조건·준비 절차 표시 | 정책 우선순위와 다음 행동 갱신, 준비 문서 반영 |

상세 화면은 긴 자기소개를 다시 요구하는 화면이 아니다. 질문이 정교해진다는 것은 정책 후보를 구분하는 사실과 사용자의 제약·선호를 더 정확히 확인한다는 뜻이다.

### 4.5 전환 조건과 사용자 선택

- 전환 제안의 계기는 사용자가 관심 정책을 고르거나 혜택·신청 준비를 더 알아보려는 행동이다. 카드 몇 개를 눌렀다는 이유만으로 상세 화면을 강제하지 않는다.
- ‘관심을 보임’은 내면의 의지나 심리 상태를 AI가 추측하는 뜻이 아니다. 선택·요청 등 명시적 행동과 사용자의 전환 선택을 기준으로 한다.
- 정책 후보나 다음 행동을 구분할 추가 정보가 있을 때 전환을 제안한다. 이미 정보가 충분하면 바로 결과를 안내한다.
- 제안 문구 예: **“선택한 지원을 더 자세히 확인해볼까요? 필요한 조건만 조금 더 물어볼게요.”**
- 선택 버튼 예: **“더 자세히 확인하기” / “지금 안내로 계속하기”**. ‘지금 안내’는 신청 자격이 확인되었다는 의미가 아니다.
- 이전 선택은 상세 화면에 이어받고 수정할 수 있게 한다. 새로 필요한 질문을 하나씩 또는 짧은 묶음으로 제시하고, 왜 묻는지 설명한다.
- 모름·건너뛰기·기존 안내로 돌아가기를 제공한다. 상세 질문을 중단해도 이전 답변과 확인된 결과를 유지한다.
- 핵심 신청 조건은 관심 전환을 기다리느라 확인을 미루지 않는다. 정책을 개인에게 맞는 것으로 구체적으로 안내하려면 필요한 나이·거주지 등 기초 조건을 앞 단계에서 확인하고, 확인하지 못한 조건은 미확인으로 표시한다.
- 상세 정보 제공을 원치 않는 사용자에게 사실과 근거가 불명확한 추천을 확정적으로 제시하지 않는다. 남은 조건 확인 방법이나 상담 준비를 안내한다.

### 4.6 상세 질문의 예와 다음 행동

아래는 질문 설계 예이며, 특정 정책의 실제 자격 조건을 뜻하지 않는다. 선택한 공식 정책에 필요한 항목만 사용한다.

| 관심 방향 | 상세 확인할 수 있는 정보 | 서비스가 활용할 부분 |
|---|---|---|
| 주거·월세 | 현재 거주 형태, 계약 상태, 해당 정책에 필요한 소득·가구 기준의 확인 가능 여부 | 주거 정책 후보·조건 확인과 서류 준비 경로 |
| 취업·교육 | 현재 활동 상태, 원하는 직무·교육, 참여 가능한 시간과 방식 | 지원 후보와 이용 부담을 고려한 우선순위·준비 행동 |
| 생활비 부담 | 현재 필요한 지원, 해당 정책의 소득·가구 조건을 확인할 수 있는지 | 재정 지원 방향·확인할 조건·상담 질문 |
| 상담 받기·모르겠음 | 먼저 이야기하고 싶은 분야, 가능한 연락·상담 방식 | 상담용 상황 요약과 기관 문의 초안 |

자격에 영향을 주는 사실과 ‘온라인 활동 선호’, ‘참여 가능 시간’ 같은 선호는 구분해 저장·활용한다. 선호는 정책 우선순위와 다음 행동에 반영하며, 자격 조건으로 바꾸어 해석하지 않는다.

소득·가구 등 상세 정보를 추가로 확인할 때에도 필요한 최소 범위와 질문 목적을 안내한다. 정확한 값을 모르면 확인 경로를 제시하고, 불필요한 개인정보를 수집하지 않는다. 추가한 답변은 기존 사실과 구분해 사용자에게 수정·확인 기회를 제공한다.

**팀이 공유할 예시 흐름:** ‘쉬고 있어요’ → ‘생활비 부담 줄이기’ → 지원 방향·기초 조건 확인 → 관심 있는 지원을 선택 → ‘더 자세히 확인하기’ 선택 → 필요한 조건·선호 확인 → 후보와 준비 행동 갱신. 처음에 정책명을 모르거나 상세 설명이 어려워도 시작할 수 있고, 참여 의향이 생긴 뒤 필요한 정보를 보완한다.

## 5. 기존 방식과 차별점

| 비교 대상 | 이미 제공하거나 구현한 내용 | 이 프로젝트에서 집중할 부분 |
|---|---|---|
| yurimakes 기존 MVP | 사용자 조건 평가, 자연어 관심사 검색, 공식 정보 기반 LLM 설명 | 적은 카드 선택으로 시작하고 필요한 질문과 준비 행동까지 연결 |
| 온통청년 | AI 맞춤 추천, 정책 진입상담 | 기존 기능을 참고하며 청년 직접 이용 흐름과 시작 부담을 검증 |
| 열고닫기 | 설문 추천, AI 상담사 베타 | 설문·AI 도입 자체보다 답변에 따라 질문과 준비 과정을 연결하는 효과를 검증 |
| 정부 AI국민비서 통합 | 정부24·국민비서·혜택알리미 연계 추진 | 현재 운영 기능과 추진 계획을 구분해 비교하고 청년의 초기 이용 흐름에 집중 |

맞춤 추천, 카드 UI, AI 상담이 최초의 기능이라고 주장하지 않는다. 다른 서비스가 준비·상담 기능을 전혀 제공하지 않는다고 단정하지 않는다. 차별점은 **정책을 찾아보지 않던 청년이 적은 입력으로 시작하고, 관심이 생기면 상세 확인 단계로 이어져 조건·선호를 보완한 뒤 정책과 준비 행동을 갱신하는 것**이다. 시작 부담을 낮추는 효과와 추가 정보가 추천·에이전트의 다음 행동 품질을 높이는 효과를 함께 검증한다.

비교 검증의 기본 기준은 내 기존 MVP의 조건·관심사 입력 방식이다. 외부 서비스는 기능·이용 흐름 참고 대상이며, 외부 서비스까지 직접 사용자 비교시험에 포함할지는 별도로 정한다.


## 6. AI의 역할과 기술 구성

### 6.1 AI가 필요한 지점

고정 카드 선택값 처리와 명확한 조건 비교는 코드로 처리할 수 있다. AI는 짧은 일상 표현을 지원 분야와 연결하고, 이전 답변과 여러 정책의 조건을 함께 고려하며 질문의 상세 수준·순서·설명·준비 문서를 정하는 데 활용한다. 사용자가 상세 확인을 선택하면, 이미 확인한 사실과 후보를 구분할 부족한 정보에 따라 다음 질문을 제안한다. 전환 버튼과 사용자의 선택, 필수 조건 검증은 코드로 관리한다. 모든 동작에 LLM을 호출하는 구조를 목표로 하지 않는다.

| 구분 | 맡는 역할 |
|---|---|
| 규칙·코드 | 카드 값과 고정 분기, 명확한 연령·지역·신청기간 비교, 날짜·형식·정책 식별값 검증 |
| LLM | 상황·목표 정리, 맥락에 따른 질문·지원 방향·다음 행동 제안, 근거 기반 설명과 문서 초안 |
| 검색·데이터 | 공식 정책 후보와 근거 조회, 원문·버전·변경 이력 관리 |
| 사용자·기관 | 부족한 사실 확인, 복잡한 소득·가구·예외 조건 확인, 최종 신청 자격 확인 |

### 6.2 입력·처리·결과

- 입력: 상황·목표·관심 카드, 상세 확인 선택, 단계별로 확인한 조건·선호, 선택적인 짧은 자유 입력.
- 처리: 확인된 사실·선호와 모르는 내용을 분리하고 지원 방향을 제안한다. 공식 정책 후보와 근거를 조회하고, 결과를 구분할 필요한 조건 확인 질문이나 다음 행동을 선택한다. 상세 단계의 새 답변으로 후보·우선순위·준비 행동을 갱신하고 갱신 이유를 설명한다.
- 결과: 관련 정책과 이유, 확인된 조건과 추가 확인사항, 현재 할 수 있는 행동, 준비물 체크리스트·발급 안내·상담 요약·문의 초안.

‘에이전트’는 자유롭게 정책을 추측하거나 자동 신청하는 기능을 뜻하지 않는다. 확인된 답변과 진행 상태를 관리하면서 상황 정리·검색·조건 확인·문서 생성 도구를 이어 실행하는 구조를 뜻한다.

### 6.3 개발 예정 기술

| 기술 | 사용 목적 | 상태 |
|---|---|---|
| React·TypeScript | 모바일에서도 이용할 수 있는 카드형 웹 화면 | 개발 예정 |
| FastAPI | 화면과 연결되는 서버 API | 개발 예정 |
| PostgreSQL | 정책 데이터와 필요한 진행 상태 관리 | 개발 예정. 대화 저장 범위는 자문 후 결정 |
| LangGraph | 확인된 답변·부족한 정보·후보·도구 실행과 간편/상세 질문 단계 연결 | 개발 예정 |
| OpenAI API 기반 LLM | 기존 활용 경험을 출발점으로 상황·질문·설명·문서 기능 구성 | 최종 모델·API 제공 경로는 미확정 |
| text-embedding-3-small | 기존 임베딩 활용 경험에 따른 초기 비교 후보 | 지원 플랫폼 제공 범위와 조건 확인 필요 |
| pgvector·BM25 | 의미 검색과 키워드 검색 결합 | 개발·효과 검증 예정 |
| RAG | 검색된 공식 근거를 설명과 문서 생성에 제공 | 개발·효과 검증 예정 |
| Pydantic | 생성 결과의 형식과 필드 검증 | 개발 예정. 사실 검증은 공식 근거 대조로 별도 수행 |
| Docker | 웹서비스 실행 환경 구성 | 배포 예정. 호스팅 환경은 별도 결정 |

별도 GPU 환경 구축과 자체 모델 학습은 초기 범위에 포함하지 않는다. 모델은 지원 플랫폼의 API 제공 범위·이용 조건을 확인한 뒤 선정한다. OpenAI 관련 경험을 적었다고 해서 지원 플랫폼이 해당 API를 제공하거나 비용을 지원한다고 가정하지 않는다.

상황 정리에는 경량 모델을, 복잡한 근거 해석에는 필요한 경우 고성능 모델을 쓰는 방식을 비교한다. 단계별 모델 분리는 확정된 운영 구성이 아닌 평가할 후보이다. 정책 임베딩은 미리 생성하고 정책 변경 시 갱신한다. 근거 검색 결과 재사용은 정책 버전과 조건에 맞춰 적용하고, 다른 사용자의 개인정보가 섞이지 않도록 설계한다.

진행 상태에는 간편/상세 질문 단계, 사용자의 전환 선택, 확인된 사실과 선호, 이미 물은 질문·건너뛴 항목, 남은 확인사항, 현재 정책 후보를 구분해 관리한다. 상세 단계에서도 같은 질문을 반복하지 않고 이전 단계로 돌아갈 수 있도록 한다. 정보가 충분한지는 LLM이 만든 확신 점수만으로 판단하지 않고, 후보와 다음 행동에 필요한 항목의 확인 여부를 기준으로 한다.

모델 구성은 핵심 사실 일치율, 응답시간, 요청당 비용으로 비교한다. 사용량·호출 제한·실패 단계를 기록하고, AI 오류가 발생해도 확인된 조건과 공식 안내를 유지한다.

## 7. 정책 데이터, 조건 확인과 문서 생성

### 7.1 정책 데이터

- 온통청년 API와 이용 조건을 확인한 지자체·사업 운영기관의 공식 공고를 활용한다.
- 정책 ID, 지원 내용, 조건, 신청기간, 필요 서류, 공식 URL과 근거를 정리한다.
- 수집·정규화, 필수 항목, 중복, 갱신 시각, 버전과 변경 이력을 관리한다.
- 기관의 공식 양식과 발급 안내는 체크리스트와 준비 문서의 근거로 사용한다.

### 7.2 조건 상태

| 사용자에게 보일 상태 | 뜻 |
|---|---|
| 확인됨 | 확인한 입력과 비교 가능한 조건이 일치함. 전체 신청 자격 확정은 아님 |
| 조건에 맞지 않음 | 비교 가능한 조건에 명확한 불일치가 있음 |
| 확인 필요 | 정책 조건·근거가 복잡하거나 기관 확인이 필요함 |
| 사용자 입력 부족 | 해당 조건을 비교할 사용자 정보가 부족함 |

현재 코드의 MATCH·UNKNOWN·NO_MATCH와 위 네 가지 표시 상태의 매핑은 개발 시 정한다. UNKNOWN의 원인을 정책 정보의 불확실성과 사용자 입력 부족으로 구분할 수 있도록 보완한다. 사용자 상태를 카드 한 장으로 과도하게 추정하거나 최종 자격을 LLM이 확정하지 않는다.

### 7.3 문서 생성

- 준비물 체크리스트
- 서류 발급 경로 안내
- 상담용 상황 요약서
- 기관 문의 초안

문서에는 확인한 사실, 남은 질문과 공식 근거를 구분한다. 생성 문서는 사용자가 확인한 뒤 다운로드하고 필요한 기관에 직접 전달하는 방식으로 계획한다. 자동 제출·자동 연락은 초기 범위에 포함하지 않는다. 문서 생성은 다음 행동을 쉽게 만드는 준비 보조 기능이다.

## 8. 현재 MVP와 앞으로 개발할 기능

| 구분 | 현재 MVP | 이번 프로젝트의 고도화 계획 |
|---|---|---|
| 사용자 입력 | 나이·지역·취업상태, 선택적인 자연어 관심사 | 간편 카드 → 사용자가 선택한 상세 질문 화면. 기존 답변을 이어받아 조건·선호를 보완 |
| 화면·저장 | Streamlit·SQLite | React·TypeScript·FastAPI·PostgreSQL |
| 데이터 | 온통청년 API 수집·정규화·원본 보존·SQLite 적재 | 공식 공고 근거와 필요 서류 구조화, 갱신·버전 관리 보완 |
| 검색·설명 | OpenAI 임베딩·FAISS와 공식 정보 기반 LLM 설명 | 키워드·의미 검색, RAG, 단계별 근거 검증 |
| 진행 관리 | 입력 후 정책 결과를 제시하는 흐름 | 간편/상세 단계, 전환·중단·복귀, 답변·부족한 정보·후보·다음 행동을 연결하는 상태 관리 |
| 준비 문서 | 아직 구현하지 않은 범위 | 체크리스트·상담 요약·문의 초안 |
| 검증·배포 | 2026년 7월 기록상 자동 테스트 122개와 로컬 통합 실행 | 새 기능 평가 사례와 청년 실제 테스트, 웹 배포·운영 지표 |

122개 테스트는 과거 기능 검증 기록이며, 이번 에이전트의 품질이나 사용자 효과를 입증한 수치가 아니다. 과거 실제 API 통합 검증 20건과 앞으로 다룰 정책 20~30개도 구분한다. 기존 테스트는 재사용·보완하되 상황 해석, 질문 선택, 검색, 설명·문서 오류를 새로 검증한다.

개발 단계는 카드형 시작 화면 → 선택적 상세 질문 화면과 답변 이어받기 → 질문·진행 상태 → 정책·조건 확인과 결과 갱신 → 준비 문서 → 배포와 실사용 검증 순으로 정리한다. 청년 참여자 테스트는 최종 완성 후에만 하는 것이 아니라 문구·흐름의 초기 확인과 전체 서비스 검증에 활용한다. 단계별 일정과 모집 방법은 팀에서 정한다.

## 9. 검증 계획과 기대효과

### 9.1 기술 검증

| 항목 | 현재 목표 |
|---|---|
| 평가 사례 | 연령·지역·마감·복합 조건 등을 포함한 100건 이상 |
| 명확한 제외 조건을 놓치는 오류 | 평가 사례에서 0건 목표 |
| 미확인 조건을 충족으로 단정하는 오류 | 평가 사례에서 0건 목표 |
| 금액·기간·서류 등 핵심 안내의 근거 일치율 | 95% 이상 목표 |
| 추가 점검 | 정책 관련성, 필요한 질문 누락, 상세 단계 답변 반영·중복 질문·중단 후 복귀, 근거 누락, 문서 필수 내용 누락 |

위 수치는 달성 결과가 아닌 목표이다. 평가 사례의 정답과 측정 기준을 정의하고, 실패 원인을 기록한 뒤 수정·재평가한다. 122개 기존 자동 테스트와 100건 이상 평가 사례는 서로 다른 검증이다.

### 9.2 청년 참여자 실제 테스트 (보류)

- 대상: 정책 이용 경험이 적거나 탐색·준비를 중단한 청년 20명.
- 비교 기준: 기존 MVP의 조건·관심사 입력 방식.
- 측정: 첫 관련 정책 도달 시간·도달률, 질문 수와 부담, 상세 질문 전환·완료·이탈, 조건 이해·준비물 확인·상담·문의 실행 여부와 이유.
- 구분: 링크 클릭, 문서 다운로드, 준비 완료, 상담·문의 실행은 각각 다른 행동으로 기록한다.
- 모집 경로: 청년센터·대학 상담창구 등에서 협력 가능성을 검토한다. 확정된 모집·협약으로 표현하지 않는다.
- 담당자용 서비스를 1차로 선택하면 상담 담당자 검증과 과제를 추가로 설계한다. 인원은 미정이며, 청년의 부담·효과 검증을 어떻게 함께 할지도 다시 정한다.


### 9.3 단계적 질문 보완 기능의 검증

**핵심 검증 질문:** 간편 카드가 시작 부담을 낮추면서, 선택적 상세 질문이 정책 관련성·조건 확인과 다음 행동의 적절성을 개선하는가? 질문을 더 받는 사용자에게 중도 이탈이 커지지는 않는가?

- 기술 평가에서는 동일한 사용자 사례에 대해 간편 단계 정보만 제공한 결과와 필요한 상세 정보를 보완한 결과를 비교한다. 정답·필수 질문·적절한 다음 행동은 사례별로 정의한다.
- 정책 관련성, 후보를 구분하는 필요한 정보의 확인 정도, 불확실성의 올바른 표시, 다음 행동의 적절성과 문서 누락을 함께 평가한다. 추천이 바뀌었다는 사실만으로 품질이 좋아졌다고 판단하지 않는다.
- 사용자 테스트에서는 기존 MVP와 비교하되, 간편 진입의 효과와 상세 전환의 효과를 구분한다. 청년 20명은 전체 검증 목표이며, 비교 방식은 참가자의 부담과 순서 효과를 고려해 설계한다.
- 상세 전환율은 ‘제안받은 사용자 중 상세 확인을 선택한 비율’, 완료율은 ‘전환한 사용자 중 필요한 확인을 마친 비율’로 구분한다. 높은 전환율만을 성공으로 삼지 않고 질문 부담·완료·실제 행동과 함께 본다.
- 상세 단계의 질문 수·소요시간·이탈 이유와 추가 정보를 반영한 정책·행동 품질을 함께 기록한다. 더 질문하지 않아도 충분한 사용자에게는 질문을 늘리지 않는지 확인한다.
- 상세 전환을 선택한 사람과 선택하지 않은 사람의 결과 차이는 관심·상황 차이의 영향을 받을 수 있다. 이 차이만으로 상세 질문의 효과를 단정하지 않는다.
- 전환을 거절하거나 중단한 사용자도 기존 안내와 기관 확인 경로를 이용할 수 있는지 점검한다.

### 9.4 목표 산출물과 발전 계획

사업기간 안에 간편 카드와 선택적 상세 질문 화면, 결과 갱신, 준비 문서를 실제로 이용할 수 있는 웹 MVP로 구현·배포한다. 정책 이용을 시작하기 어려운 청년의 부담을 줄이고, 상담 담당자가 확인된 상황과 남은 질문을 파악하는 데 도움을 주는 효과를 기대한다.

지원 종료 후 유지할 모델·클라우드 비용을 확인하고 기관의 유입·실증·도입 가능성을 검토한다. 사업화나 기관 도입을 확정된 성과로 적지 않는다.

## 12. (추가) 신청서에 반영할 핵심 강조 문장

> 최소 질문 카드는 정책을 찾아보지 않던 청년의 시작 부담을 낮추는 진입 방식이다. 사용자가 관심 정책을 선택하거나 더 자세한 안내를 원하면 기존 답변을 이어받는 상세 질문 화면으로 전환하고, 필요한 조건과 선호를 단계적으로 확인한다. 추가 정보를 반영해 정책 우선순위와 다음 행동을 갱신하여, 간편한 시작과 충분한 정보에 근거한 안내를 함께 구현한다.

- 문제·차별점 문항: 적은 입력의 정보 부족을 인정하고 관심 이후의 상세 확인으로 보완하는 흐름을 강조한다.
- 구현 문항: 간편/상세 화면, 전환 선택, 기존 답변 이어받기·수정, 중단·복귀와 결과 갱신을 기능으로 반영한다.
- AI 활용 문항: 확인된 답변·부족한 정보·정책 후보에 따라 상세 질문과 다음 행동을 정하는 역할을 설명한다.
- 최종 목표·검증 문항: 진입 부담뿐 아니라 상세 질문의 완료·이탈, 정책 관련성과 다음 행동의 적절성을 함께 평가한다.

이 절은 신청서에 반영할 요지이며 전체 문항의 글자 수를 다시 맞춘 최종 완성본은 아니다. 구현 상태는 계속 개발 예정으로 표시한다.

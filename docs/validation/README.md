# 데이터·API 구현 검증

[서비스 소개](../../README.md) · [개발자 실행 안내](../getting-started/README.md) · [API 규격](../api/intake-v1.md)

기존 정책 파서·SQLite 저장소·조건 평가·FastAPI가 연결되는 경로를 재현한다. **기존 예제 snapshot 10개 정책을 고정 날짜로 재생하는 검증**이며, 현재 모집 정책 확보 실적이나 실제 사용자 평가 결과가 아니다. 공개 Vercel 데모는 계속 가상 체험 모드다.

## 한 명령으로 연결 재현

Python 3.10 가상환경과 `requirements-api.txt`를 준비한 뒤 저장소 루트에서 실행한다. 전체 설치 방법은 [환경 준비](../getting-started/README.md#로컬-환경-준비)를 참고한다.

```powershell
.\.venv\Scripts\python.exe scripts/replay_policy_api.py --output .policy-evidence/replay.json
```

API 키·실제 정책 DB·외부 AI 호출·별도 서버 프로세스가 필요하지 않다. 임시 SQLite에 기존 예제를 적재하고, 정책 provider를 가짜 함수로 대체하지 않은 실제 FastAPI에 TestClient HTTP 요청을 보낸다. 종료하면 임시 DB를 삭제하고 JSON 증빙만 남긴다.

| 검증 범위 | 확인 내용 |
|---|---|
| 데이터 연결 | 예제 10개 파싱·SQLite 적재 수 일치, DB readiness, 원본 행 10개의 정규화 값·위치·SHA-256 추적 |
| 정책·질문 연결 | 상황 카드가 사실을 추정하지 않음, API 후보의 정책명·출처 보존, 직접 입력한 나이·지역 비교, 미입력 취업 상태와 미확인 자격의 상태 유지 |
| 진행·재평가 | 상세 동의 후 중단·복귀와 답변 재사용, 준비 단계 도달, 나이 수정과 모집기간 만료에 따른 후보 제외, API·감사 후 DB 불변 |

총 **13개 연결·동작 검사**다. 검사 하나라도 실패하면 명령이 실패하며, 실패 실행을 성공 보고서로 저장하지 않는다. JSON에는 검사별 결과, Python 버전, 소스·fixture SHA-256, 정책 수·원본 추적·필드 완전성이 포함된다. API 응답 스키마 검증과 기존 회귀 테스트는 별도로 계속 실행한다.

기준일은 `2026-06-28`, 만료 재평가 날짜는 `2026-10-08`로 고정했다. 기존 예제 값을 최신 모집기간으로 바꾸지 않는다. 과거 날짜 재현은 운영 서버의 한국 기준 현재 날짜와 구분되며, 운영 API는 클라이언트가 판정 날짜를 지정할 수 없다.

## 실제 로컬 정책 DB 점검

기존 수집기로 준비한 DB와 보존한 원본 JSON을 사용한다. 아래 경로는 예시이며 실제 파일 위치로 바꾼다. 여러 페이지는 `--snapshot`을 반복해 모두 전달한다.

```powershell
.\.venv\Scripts\python.exe scripts/audit_policy_data.py --db data/processed/policies.sqlite3 --snapshot data/raw/page_1.json --snapshot data/raw/page_2.json --reference-date 2026-10-08 --output .policy-evidence/data-audit.json --strict
```

`--reference-date`를 생략하면 한국 기준 오늘을 사용한다. 감사는 기존 DB를 **읽기 전용**으로 열며 없는 DB를 생성하지 않는다. 이 도구는 표준 라이브러리만 사용하고, 키·원격 API·LLM이 필요하지 않다.

| 보고 항목 | 해석 |
|---|---|
| 정책 수·필드 완전성 | 각 필드의 값 있음/결측 수와 비율. 분모는 읽은 고유 정책 수이며 빈 DB 비율은 `null`. 값이 있다는 것이 정확함을 뜻하지 않음 |
| 지역 코드·분야별 수 | DB에 기록된 범위. 여러 지역을 가진 정책은 여러 코드에 집계되므로 지역별 합계는 정책 수와 다를 수 있음. 전국 모든 공고의 확보율이 아님 |
| 신청기간 | 기록된 기간 안/시작 전/마감/확인 불가를 구분. 저장된 OPEN 값만으로 현재 모집을 확정하지 않음 |
| 미입력 조건 상태 | 사용자 답변 없이 같은 판정 로직으로 측정. 정책 근거 부족과 사용자 입력 부족을 구분하며 최종 신청 자격을 확정하지 않음 |
| 처리 시각 | `last_verified_at`과 기준일의 차이. 기존 naive 시각은 수집기의 UTC 규칙에 맞춰 해석. 기관이 공고를 재검증한 날짜가 아님 |
| 원본 추적 | ID만 일치하는 것과 실제 정규화 필드가 일치하는 것을 구분. 원본 snapshot SHA-256과 0부터 시작하는 행 위치를 보존 |

원본 대조는 현재 파서를 재실행해 DB 값과 비교한다. 수집 시각과 날짜에 따라 변하는 `last_verified_at`, `application_status`는 대조에서 제외하고 나머지 모델 필드를 비교한다. 같은 ID가 여러 원본에 등장하면 일치하는 행을 기록하고 정책 수는 중복 집계하지 않는다. `trace_compared_fields`에 비교 필드가 명시된다. 이것은 원본과 정규화 결과의 연결 확인이며, 파서 자체의 정확성·공식 공고 최신성·데이터 이용허락 검증을 대신하지 않는다.

URL 검사는 HTTP(S) 주소 형태만 확인하며 공식 기관 여부나 링크 응답을 보장하지 않는다. 서류가 비어 있어도 ‘제출 서류 없음’으로 바꾸지 않는다. 모든 값이 채워졌거나 원본 추적이 일치해도 G2 통과나 운영 준비 완료로 표시하지 않는다.

| 종료 코드 | 의미 |
|---|---|
| `0` | 감사 결과 생성. `--strict`가 있으면 아래 증빙 누락도 없음 |
| `2` | DB·snapshot·출력 경로 등의 입력 오류. 원본은 변경하지 않음 |
| `3` | `--strict` 증빙 누락: 빈 DB, 사용할 수 없는 URL, 원본 미제공·ID 없음·정규화 불일치. JSON의 `evidence_blockers`에서 확인 |

실제 DB·원본·감사 보고서는 로컬에 유지한다. 기본 증빙 폴더 `.policy-evidence/`는 Git에서 제외하며, 실제 데이터 보고서를 공개하기 전에는 재배포 가능 범위와 포함 정보를 확인한다.

## 자동 검증과 현재 범위

[Demo checks](https://github.com/yurimakes/youth-policy-llm-recommender/actions/workflows/demo-checks.yml)는 기존 Python·JavaScript·빌드·브라우저 검증에 위 오프라인 API 재생을 추가한다. 성공 실행의 `policy-validation-evidence` 아티팩트에서 `replay.json`을 내려받을 수 있다. 아티팩트는 30일 보관하며 같은 커밋에서 다시 생성할 수 있다. 예제 보고서에는 실제 사용자 답변을 사용하지 않는다.

기존 예제 기준 측정값은 정책 10개·원본 추적 일치 10개, 신청기간 값 있음 7/10, 제출서류 값 있음 3/10이다. `2026-06-28` 기준 기간 분류는 기록된 기간 안 4개·마감 2개·시작 전 1개·확인 불가 3개다. 이 수치는 예제 데이터의 완전성과 동작을 설명하며 실제 정책 확보율·추천 정확도·사용성 점수가 아니다.

**G2는 진행 중인 목표**다. 운영 대상 정책 20–30개 선정·공식 근거 대조와 100건 이상의 독립된 정답 평가가 추가로 필요하다. 새 도구는 그 데이터를 측정하고 기존 흐름과 연결을 재현하기 위한 기반이다. [개발·검증 계획](../development-plan.md)

# 사업기간 개발·검증 계획

기준일: 2026-10-08 · 목표 기간: 2026년 10월부터 12월 11일까지

이 문서는 공개 가능한 기능 범위와 검증 기준을 정의한다. 아래 일정과 수치는 **개발 목표**이며 완료 실적이 아니다. 각 Gate는 구현과 검증 증빙을 함께 갖춰야 통과한다. 다음 Gate의 구현·검증은 앞 Gate의 통과 증빙을 확보한 뒤 시작한다.

## 1. 현재 구현과 출발점

현재는 **Foundation: 데모·규칙·로컬 API 기반 구현 단계**다. 구현된 데모와 로컬 API를 기준선으로 재사용하며, G1–G5는 각 완료 기준에 따른 검증이 필요하다.

| 구분 | 현재 구현 | 추가 검증·구현 범위 |
|---|---|---|
| 화면 | 상황·관심 카드, 기초 질문, 선택적 상세 확인, 답변 수정·중단·복귀 | 실제 정책을 이용한 개인화 질문과 모바일 이용 검증 |
| 정책·조건 | 온통청년 수집·정규화·SQLite, 조건 평가, 로컬 Intake API | 지역·분야별 데이터 범위와 공식 근거, 복합 조건 회귀 검증 |
| 장바구니·문서 | 메모리 장바구니, 준비 체크, 입력을 조합한 상담 초안·복사·브라우저 PDF | 공식 정책 근거를 연결한 체크리스트·발급 안내·상담 문서 |
| AI | 기존 Streamlit MVP의 OpenAI 임베딩·FAISS 검색·설명 | 새 Intake 흐름의 최소 질문 개인화, 근거 검색·문서 생성 통합 |
| 배포 | Vercel의 가상 데이터 정적 데모, 실제 API는 로컬 실행 | 실제 정책 API를 연결한 웹/PWA와 운영 검증 |

기준 코드는 [`d9b0176`](https://github.com/yurimakes/youth-policy-llm-recommender/commit/d9b0176b637ab06d186cb8a05ae88cba31ac3240)이다. [기반 코드 자동 검증](https://github.com/yurimakes/youth-policy-llm-recommender/actions/runs/37770855936)은 Python·JavaScript·정적 빌드·브라우저 흐름 검사이며, 전국 정책 coverage나 AI 품질·사용자 효과를 입증한 결과는 아니다. 공개 데모의 가상 정책과 별도 공식 참고자료도 실제 정책 데이터 검증을 대신하지 않는다.

## 2. 월별 구현 범위

| 시기 | 서비스 대상·데이터 범위 | 구현할 기능 | 완료 증빙 |
|---|---|---|---|
| 10월 · 기반 구현 | 서울·경기 지역 정책과 전국 공통 정책. 주거·취업 중심의 초기 정책 20–30개를 검증 대상으로 선정 | 공식 정책 적재·근거 추적, 카드 탐색, 기본 후보·조건 확인, 일부 정책의 상세 질문. G1·G2 | 데이터 범위표·원문 추적표, 정답 평가 세트, 규칙·진행 회귀 결과 |
| 11월 · 기능 확대 | 이용허락이 확보된 전국 지역 정책을 순차 수집·적재 | 지역별 조건 판정 확대, 최소 질문 개인화, 공식 공고 근거 검색, 준비·상담 문서 생성. G3·G4 | 질문 기준선 비교, 검색 비교, 문서별 근거 대조와 오류 재평가 |
| 12월 1–11일 · 운영 검증 | 전국 거주 청년이 이용하는 웹/PWA. 확보·검증한 정책 범위를 명시 | 실제 정책 API 연결, 모바일·PWA 배포, 오류 복구, 응답시간·비용·사용성 검증. G5 | 공개 endpoint 점검, 모바일/PWA 결과, 사용성 관찰과 수정 후 재평가, 릴리스 버전 기록 |

전국 이용 대상과 전국 모든 정책 확보는 다른 기준이다. 지역·분야별 수집 범위와 누락을 공개 가능한 범위표로 표시하며, 미수집·미확인 정책의 조건을 추정해 채우지 않는다. 일정이 도래해도 Gate 미통과 기능은 완료로 표시하지 않는다.

## 3. G1–G5 Gate

현재 **G1 미통과**, G2–G5도 미통과다. 기존 코드의 일부 기능이 있더라도 아래 증빙을 갖춰야 해당 Gate를 통과한다.

| Gate | 구현 범위 | 완료 기준 | 다음 단계 |
|---|---|---|---|
| **G1 Data · 정책 데이터** | 정책 적재, 지역·분야·기간·조건·서류·출처 구조화, 원본 추적 | 초기 정책 20–30개의 ID·공식 URL·확인 시각·원본 위치를 추적 가능. 지역·분야·필드 coverage와 결측을 측정하고, 자동 비교 가능한 조건과 기관 확인이 필요한 조건을 구분 | 실제 정책을 이용한 규칙·질문 기준선 |
| **G2 Core QA · 규칙과 진행** | 나이·거주지·기간 등 비교, 네 가지 조건 상태, 기본·상세 질문, 답변 수정·중단·복귀 | 정답 평가 사례 100건 이상에서 명확한 제외 조건 누락 0건, 미확인 조건을 충족으로 단정한 사례 0건. 경계값·정책 만료·모름·건너뛰기·복합 조건·후보 없음·오류 복구를 회귀 검사 | 검증된 조건 로직 위에 질문 개인화 연결 |
| **G3 Question · 최소 질문 개인화** | 맥락에 따른 질문 선택·순서·설명, 사용자 확인 후 답변 반영, 단계별 진행 연결 | 동일 사례·동일 필수조건 확인 수준에서 고정 질문 기준선보다 평균 질문 수 감소. 이미 확인한 답변의 중복 질문, 카드에서 사실 추정, 동의 없는 상세 진입이 평가 사례에서 0건. 모델 실패 시 기본 경로 유지 | 근거 검색·문서 생성 연결 |
| **G4 Evidence · 근거 검색과 문서** | 공식 공고 문단 검색, 근거 연결 설명, 준비물·발급 안내·상담 요약·문의 초안 | 검색 정답 세트의 고정 subset에서 의미 검색을 결합한 방식이 키워드 기준선보다 Recall@5 개선. 생성 문서의 핵심 안내 근거 일치율 95% 이상, 검증 사례에서 근거 없는 금액·기간·서류 생성 0건. 규칙 판정은 유지 | 검증된 AI 기능만 운영 API에 적용 |
| **G5 Release · 웹/PWA와 운영** | 실제 정책 API 배포, 모바일/PWA, timeout·fallback·비용 제한, 사용성 검증 | 공개 endpoint·계약·잘못된 입력·모델 실패·timeout·fallback·모바일/PWA 검사 통과. 응답시간·비용이 평가 전에 고정한 예산 이내. 청년 사용성 검증과 수정 후 재평가를 완료하고 재현 가능한 릴리스 기록 확보 | 검증 범위를 명시한 운영 버전 |

위 오류 0건·100건·95%와 질문·검색 개선은 **통과 목표**다. 통과하더라도 평가 세트 밖의 모든 사례에서 오류가 없거나 최종 신청 자격이 보장된다는 뜻은 아니다.

## 4. 평가 방법과 증빙

| 평가 영역 | 측정 방법 | 남길 증빙 |
|---|---|---|
| 데이터 coverage | 확보한 목록에서 지역·분야별 정책 수와 필드별 값/결측 비율 측정. ID·공식 URL·확인 시각·원본 추적은 전 항목 검사 | 목록의 버전·분모·수집 범위, 필드 완전성, 원문 대조 결과. 전국 모든 공고의 확보율로 표현하지 않음 |
| 규칙·진행 | 공식 조건과 검증용 입력에 대한 기대 상태·제외 여부·다음 행동을 먼저 정한 정답 세트로 비교 | 사례 ID, 기대값·실제값, 오류 유형, 수정 후 회귀 결과 |
| 최소 질문 | 같은 입력·정책·확인할 필수조건으로 고정 질문과 개인화 질문을 비교. 질문 수는 조건 확인 수준과 함께 측정 | 평균 질문 수, 필수조건 확인율, 중복 질문·불필요한 질문·중단/복귀 결과 |
| 검색 | 공고 문단의 정답 근거를 지정하고 동일 snapshot·subset·Top-5에서 키워드와 의미 검색 결합 결과 비교 | Recall@5, 근거 ID·순위, 검색 시간과 비용. 평가 사례로 설정을 조정한 뒤 같은 사례를 최종 성과로 재사용하지 않음 |
| 문서 | 금액·기간·조건·서류·발급 경로 등 사실 안내를 항목 단위로 분리해 공식 근거와 대조. 근거 없음·틀린 근거·내용 불일치는 실패 처리 | 근거 일치 항목 수/전체 평가 항목 수, 문서별 출처·버전·확인 시각, 오류·수정 결과 |
| 운영 | 동일한 고정 시나리오에서 성공·잘못된 입력·데이터 없음·외부 모델 실패·timeout을 실행 | API 계약 결과, p50/p95 응답시간, 요청·세션별 호출 수·토큰·비용, fallback 결과 |
| 사용성 | 청년 20명 검증을 목표로 카드 시작→지원 후보→조건 이해→준비 문서까지 같은 과제 수행을 관찰 | 첫 관련 후보 도달 시간·도달률, 질문 부담·이탈, 미확인 조건 이해, 준비 과제 완료, 수정 후 재평가 |

청년 20명은 목표 인원이며 참여·검증 완료 실적이 아니다. 사례 수·참여자 수·정책 수를 서로 다른 지표로 기록한다. 사용성 결과에 개인 답변·연락처 등 원문을 공개하지 않고 집계·비식별 결과를 사용한다.

Gate 증빙에는 공통으로 실행 날짜, source commit, 데이터 버전, 사례/문서 버전, 환경·설정, 실패·스킵 내역을 기록한다. 스킵은 통과로 계산하지 않는다. 모델명·프롬프트·출력 스키마·토큰/호출 상한·timeout·재시도 횟수와 응답시간·비용 예산은 평가 전에 숫자와 단위로 고정한다. 예산이나 정답·분모가 정의되지 않은 평가는 Gate 통과 근거로 사용하지 않는다.

## 5. 기술 적용 순서

| 구성 | 적용 목적과 조건 |
|---|---|
| 기존 수집·조건·진행 모듈 | G1·G2의 기준선으로 재사용. AI가 명확한 조건 판정을 덮어쓰지 않도록 독립 유지 |
| React·TypeScript, FastAPI | 기존 화면 흐름과 API 계약을 재사용해 실제 정책 웹/PWA 연결. 화면 기술 전환 자체는 Gate 통과 근거가 아님 |
| SQLite, PostgreSQL | SQLite로 데이터·규칙 검증을 시작. PostgreSQL 전환은 정책 갱신·동시 접근 등 운영 요구에 맞춰 적용하고 같은 데이터·계약 회귀 결과 확인 |
| LLM과 구조화 출력 | G2 통과 후 G3에서 질문 개인화에 연결. 사용자 확인 전 해석을 자격 사실로 확정하지 않고 출력 검증·규칙·기본 경로로 제한 |
| LangGraph 등 진행 도구 | 질문·검색·문서 단계의 상태와 실패 복구를 관리할 때 적용. 기존 명시적 상태 전환보다 유지·검증에 도움이 되는 범위에서 사용 |
| 키워드·임베딩 검색과 RAG | G1의 근거 문단·G2의 안전한 조건 로직 위에 구성. G4에서 키워드 기준선 대비 개선이 확인된 범위만 채택 |

복잡한 저장소·벡터/그래프 검색·진행 프레임워크를 Gate 검증보다 먼저 도입하지 않는다. 특정 제품·모델 도입이나 코드 존재만으로 기능 검증이 완료됐다고 보지 않는다.

## 6. 기능의 경계와 미통과 시 처리

- 서비스는 정책 탐색과 신청 준비를 돕는다. 최종 자격은 공식 공고·담당 기관에서 확인한다.
- 상황 카드·선호·LLM 추측으로 취업 상태·소득·거주지 등 사실을 확정하지 않는다. 필요한 사실은 사용자가 확인하고 모름·건너뛰기를 허용한다.
- 복잡한 소득·가구·예외 조건은 검증된 규칙이 있는 정책만 상세 비교한다. 나머지는 확인 필요·입력 부족과 기관 확인 경로를 제공한다.
- 질문 개인화나 검색 개선을 입증하지 못하면 검증된 기본 질문·규칙·공식 링크 경로를 유지하며 해당 Gate는 미통과로 남긴다.
- 문서 품질 기준을 만족하지 못한 생성 기능은 운영에 적용하지 않는다. 기존의 확인한 입력·근거를 조합한 초안을 제공한다.
- 자동 신청 제출·기관 연락·상담 예약·서류 자동 발급은 사업기간 구현 범위에 포함하지 않는다.
- 기본 진행 상태는 메모리에서 유지한다. 개인정보·사용자 답변의 영구 저장은 이번 완료 기준에 포함하지 않는다. 운영 로그와 외부 모델 입력은 목적에 필요한 최소 범위로 제한하며 처리·보관·삭제 기준을 운영 전에 확인한다.
- PWA는 모바일 화면·설치·업데이트 흐름을 검증한다. 오프라인에서 최신 정책 자격을 확정하거나 사용자 답변을 자동으로 영구 저장하지 않는다.

## 7. 릴리스 버전 고정

G5 운영 버전은 다음 항목을 하나의 릴리스 기록으로 묶어 고정한다.
